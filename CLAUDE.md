# xtatic — Claude context

Static-site generator: MDX in, plain HTML out. The MDX is compiled and executed at build time; the output is pure HTML with no client-side runtime. See `README.md` for the user-facing description.

## Pipeline

`src/cli.js` → `src/index.js` `build()` → `src/paths.js` (resolve logical paths) → `src/registry.js` (lazy-compile through a per-build cache) → `src/compile.js` (MDX `compile`+`run`, with `recma-imports.js` rewriting user `import`s into resolver calls) → `src/tree.js` (assemble + apply defaults) → `src/render.js` (walk layout chain) → write to `fs`.

Each module is small and focused; read the source rather than relying on this map.

## Non-obvious invariants

- **`fs` is dependency-injected** through `build({inputDir, outputDir, fs})` for `.md`/`.mdx` reads and all writes. `.js` reads are *not* injected — they go through Node's real `import()` (see below). Memfs-only tests therefore can't reference `.js` files; tests that need `.js` use real-fs scratch dirs under `./test-tmp/<slug>/`.
- **Zip files are read as if they were directories.** `index.js` wraps the injected `fs` once via `wrapZipFs` from `src/zipfs.js` before passing it to any registry. Any path containing a `.zip/` segment (e.g. `/fonts/Inter.zip/Inter-Regular.ttf`) is intercepted: the prefix-up-to-`.zip` is read from the underlying fs, decompressed once via `fflate.unzipSync`, cached for the build's lifetime, and the rest of the path is looked up as an entry name. The interception covers `fs.readFileSync` and `fs.promises.readFile` only — `readdir`, `stat`, `writeFile`, etc. are passed through unchanged (no current call site needs them on zip-internal paths). Caveats: split happens at the *first* `.zip/` in the path, so nested zips aren't supported; matching is case-sensitive (`.ZIP` won't trigger); a literal directory named `*.zip/` will be misinterpreted as a zip and error.
- **`outputDir` is wiped at the start of every build** via `fs.promises.rm(outputDir, {recursive:true, force:true})`. This is what makes renames/deletes Just Work — the previous build's stale `index.html`s can't survive into the new tree. `assertSafeOutputDir` in `index.js` rejects `outputDir` of `/`, `.`, or anything that is the same as or an ancestor of `topDir`/`inputDir`/`layoutsDir` so a misconfiguration can't nuke source. There is no opt-out and no static-asset directory yet — every byte under `outputDir` is generated.
- **The build is two-pass when assets are involved.** `index.js` `renderTree` walks the module tree synchronously to collect `{outPath, html}` for every page (so `<Image>`, `<Style>`, `<Font>`, and the recma-assets-injected `__xtatic_asset` calls have already fired and recorded jobs into their respective registries). Then `await imageRegistry.processAll()`, `await styleRegistry.processAll()`, `await fontRegistry.processAll()`, and `await plainAssetRegistry.processAll(pages)` run in series. The plain-asset registry needs `pages` because its placement chooser scans each page's rendered HTML for tokens to derive the per-asset reference graph (which pages contain which tokens) before deciding inline vs shared vs co-located. `await assetRegistry.writeAll()` flushes everything under `outputDir/_assets/`, then `await plainAssetRegistry.writeAll()` flushes co-located files at their source-tree-mirroring positions. The four `substitute` closures are composed and applied to each page's HTML before `writeFile` — but `substitute(html, outPath)` is now page-aware (the asset substitute needs `outPath` to compute relative URLs for co-located assets). Token namespaces are disjoint (`__XTATIC_IMG_<hex>__`, `__XTATIC_STYLE_<hex>__`, `__XTATIC_FONT_<hex>__`, `__XTATIC_ASSET_<hex>__`), so substitute order doesn't matter for correctness.
- **All emitted assets go through a shared `createAssetRegistry`.** `src/assets.js` exposes `emit(bytes, ext) → '/_assets/<hash>.<ext>'` (sync, idempotent on `${hash}.${ext}` filename — same bytes with different ext gets two files, but same bytes+ext is dedupe-emitted once) and `writeAll()` (batched mkdir+writeFile at end of build). `index.js` constructs one per build and threads it into `createImageRegistry`, `createStyleRegistry`, and `createPlainAssetRegistry`. Co-located plain assets bypass `_assets/` and write to their source-tree-mirroring positions via `plainAssetRegistry.writeAll()` instead. Output URLs are always either absolute (`/_assets/…`), absolute-page-relative (co-located), or `data:` (inline) — no `basePath` config yet. No build cache across runs — every rebuild re-emits.
- **`Image` (`xtatic:image`)** — `src/image.js` `createImageRegistry({fs, topDir, assetRegistry, defaultInlineThreshold})` is built per-build and threaded through `createRegistry` so the resolver can hand each importer its own `Image` component (closure captures `importerAbsPath`, identical to `readfile` shape — `/foo` against topDir, otherwise against the importer's dir). Sharp is `import('sharp')`-loaded lazily on first job, with a clear "run npm install sharp" error if absent — it's an optional peerDep so non-image projects don't pay the install cost. SVG sources skip sharp entirely (passed through verbatim, content-addressed under their own hash). Job dedup key is `${absSrc}|${JSON.stringify(opts)}`; final `<img>` HTML is composed per-call from the job result + that call's pass-through attrs (with `className → class`, attribute escaping done in `image.js`'s own `escAttr`/`renderAttrString` since the substituted tag bypasses the JSX runtime).
- **`Style` (`xtatic:style`)** — `src/style.js` `createStyleRegistry({fs, topDir, assetRegistry, defaultInlineThreshold})` is shaped exactly like the image registry (same per-importer factory, same path-resolution rules, same token/substitute pipeline). `<Style src="...">` reads the CSS and runs `rewriteCssUrls` from `src/css-urls.js`: a regex pass over `url(...)` tokens that resolves each to `/foo` (against topDir) or `./foo`/`../foo` (against the source CSS's dir), reads the bytes, and emits them via `assetRegistry.emit`. URLs starting with `data:`, `http://`, `https://`, `//`, or `#` are passed through verbatim. Below the inline threshold (default 2KB) the rewritten CSS is emitted inline as `<style>…</style>` at the call site; above, it goes to `/_assets/<hash>.css` and the call site gets `<link rel="stylesheet" href="…">`. Pass-through attrs (`media`, `nonce`, `crossorigin`, etc.) land on whichever tag is emitted, with `className → class`. The plain-asset pipeline reuses the same `rewriteCssUrls` for `.css` files reached via plain `<link rel=stylesheet>`, so the implementation is shared (only the not-found error wording differs, passed in by the caller). Caveats: `@import "…"` (bare-string form) is NOT rewritten — only `url(...)` tokens are; if your inline CSS legitimately contains `</style>` it will prematurely close the tag (no escape attempt yet). `rewriteCssUrls` does NOT transcode `.ttf`/`.otf` references — they emit as-is, hashed. The transcode behavior moved to `<Font>` (see below); a hand-rolled `@font-face { src: url('./x.ttf') }` inside a `<Style>`-loaded CSS file ships the TTF verbatim now.
- **`Font` (`xtatic:font`)** — `src/font.js` `createFontRegistry({fs, topDir, assetRegistry, transcode, subset})` is shaped like the image/style registries (per-importer factory, dedup'd jobs, token+substitute pipeline) but designed for `<head>` use: each call expands to a `<style>@font-face{…}</style>` plus an optional `<link rel="preload" as="font" type="font/woff2" href="…" crossorigin>` when `preload`. Source handling, in priority order: if `text` is given the source is **subsetted** to just the code points in `text` (via `src/font-subset.js` `subsetToWoff2`, lazy `import('subset-font')` — HarfBuzz/WASM; new optional peerDep alongside `sharp`/`wawoff2`) and emitted as WOFF2 regardless of input ext; else `.ttf`/`.otf` are transcoded to WOFF2 via `src/font-transcode.js` (`transcodeToWoff2`, lazy `import('wawoff2')`); else `.woff`/`.woff2` pass through verbatim. Both `font-transcode.js` and `font-subset.js` serialize their calls through a module-local `queue` because each wraps a singleton WASM instance whose heap is shared across calls. The `transcode` and `subset` constructor args default to the real loaders and are overridable by tests (`test/font.test.js` stubs both). Job dedup key is `absSrc` when not subsetting, else `${absSrc}\0${canonicalSubsetText(text)}` where `canonicalSubsetText` = sorted unique code points (so `text="ab"`/`"ba"`/`"aab"` share one job+asset, but `"ab"` and `"abc"` don't, and a subsetted vs. non-subsetted reference to the same file are distinct assets). Other font metadata (family/weight/style/etc.) is still per-call and lives in the assembled `<style>` block, not the asset bytes. Always emits via `assetRegistry.emit` (no inline-as-data: URL — fonts are large and the embed is awkward); always shared `/_assets/<hash>.<ext>`, no co-located placement and no per-call inlineThreshold. Props: `src` and `family` are required; `family` is CSS-string-escaped (backslash + quote) and rejected if it contains `<` (defense against `</style>` injection in the assembled tag). `weight` accepts number or string (e.g. `"100 900"` for variable-font ranges); `style`/`display` are validated against the standard sets; `unicodeRange` is passed through to `unicode-range:` verbatim; `text` must be a non-empty string when present. Unknown extra props throw — `<Font>` does not silently pass-through arbitrary attrs (no clean place to route them across two emitted tags). Same `</style>`-in-CSS caveat as `<Style>` (no escape attempt). Token namespace `__XTATIC_FONT_<hex>__`, disjoint from the other three.
- **Plain `<img>`/`<link>`/`<script>`/`<source>`/`<audio>`/`<video>` are auto-processed.** The recma-assets plugin (`src/recma-assets.js`) walks every compiled JSX call and rewrites whitelisted `(tag, attribute)` pairs so the value flows through `__xtatic_asset(value, opts)`. It catches both shapes MDX/JSX produce: direct `_jsx('img', {src})` and `_jsx(_components.img, {src})` (markdown's `![]()` lowering — MDX maps tag names through `_components`). Whitelist: `img.src`, `script.src`, `source.src`, `audio.src`, `video.{src,poster}`, and `link.href` (only when `rel` is statically one of `stylesheet`, `icon`, `shortcut`, `apple-touch-icon`(`-precomposed`), `mask-icon`, `preload`, `prefetch`, `modulepreload`, `manifest` — non-asset rels like `canonical` are skipped because their hrefs aren't files). Dynamic `<img src={x}>` works because `__xtatic_asset` is a runtime check: non-strings, empty strings, and passthrough URLs (`data:`, `http(s):`, `//`, `#`, `mailto:`, `tel:`) are returned verbatim. Per-call escape hatch: `data-xtatic-placement="inline|shared|co-located|auto"` overrides the auto chooser; the recma plugin extracts it from the props at compile time and removes it from the output (so it doesn't leak into HTML). The `auto` chooser per source file: size ≤ `defaultInlineThreshold` (default 4KB) → inline as `data:` URL; else if used by exactly one page AND the asset's source path is at-or-below that page's output directory → co-located (mirrored to source-tree position, page-relative URL); else → shared (`/_assets/<hash>.<ext>`). Inlined `.css` referenced from `<link rel="stylesheet">` is a special case: the substitute pass replaces the whole `<link …>` tag with `<style …>CSS</style>` rather than emitting `data:text/css`, transferring all attributes except `rel`/`href` (so `media`, `nonce`, `class`, etc. carry over). recma-assets signals this by passing `{kind:'stylesheet'}` to `__xtatic_asset` for stylesheet links; only stylesheet-kind tokens trigger the tag-level rewrite, so the same CSS file referenced from a non-stylesheet `<link>` (e.g. `rel="preload"`) still gets the data: URL treatment. Same caveat as `xtatic:style`: a literal `</style>` substring in the CSS prematurely closes the inlined tag. Co-located is the only placement requiring per-page substitution: `substitute(html, outPath)` computes the URL via `path.posix.relative(pageOutDir, assetOutAbs)`. Conflicting explicit placements for the same source file throw; `co-located` requested where not viable throws. The asset registry's substitute pass HTML-escapes `&` and `"` since the substituted URL goes inside an existing `src="…"` attribute (the JSX runtime escaped the surrounding context, but the token itself bypassed escaping). Reference graph is derived post-render by regex-scanning each page's HTML for tokens — no page-tracking plumbing during render. The `__xtatic_asset` runtime closure is captured into a top-level `const __xtatic_asset = arguments[0].__xtatic_asset;` injected by recma-assets so it's reachable from inside `_createMdxContent` (where `arguments` refers to props, not the runtime). Inject only happens if a rewrite occurred. Order in `compile.js`: `[recmaImports, recmaAssets, recmaSelf]` — recma-self's pre-declare picks up the injected const, so it's not added to the destructure-from-`__xtatic_self`.
- **`childPages` and `name` are rewritten by the tool.** `childPages` is overwritten on every module with a freshly built sorted Array of direct children; `name` is set on every non-root module to its last path segment. Anything a user file exports under those names is clobbered. Spec-mandated; don't add an "input wins" override.
- **`date` and `title` are *defaulted* from `name`.** `assembleTree` parses each non-root module's name. A leading `YYYY-MM-DD` or `YYYYMMDD` (with month 01-12 and day 01-31, optionally followed by `-rest`) becomes `date`; the remainder (or the whole name when no date prefix) becomes `title` with dashes-to-spaces, run through npm `title` only if the spaced form is all-lowercase (preserves intentional casing like `THIS-is-a-TEST`). Unlike `childPages`/`name`, these are pure defaults — frontmatter or named exports win.
- **Layouts live in `layoutsDir`, not the input tree.** A page's `layout` is set either explicitly (`layout:` in frontmatter — accepts a string path resolved against `layoutsDir`, or a module object via `import`) or by the `defaultLayout` walk: `assembleTree` walks from each module up to the root and uses the first non-undefined `defaultLayout` it finds (starting at the module itself). `index.js` calls `resolveLayoutChain` *after* `assembleTree`, so string values inherited via `defaultLayout` get rewritten to the loaded module too. There's no longer any magic for files literally named `layout.md` in the input tree — those are just regular pages.
- **`childPages` is a plain `Array` sorted by `name`.** `assembleTree` rebuilds it from scratch and explicitly sorts after attach, so iteration order is guaranteed regardless of how `entries` is ordered when passed in. `index.js`'s `writeNode` reads `child.name` to derive the output path segment.
- **Frontmatter requires both `remark-frontmatter` AND `remark-mdx-frontmatter`.** The first parses the `---` block; the second turns it into an MDX export. Easy to miss — `compile.js` configures both. Frontmatter keys are then promoted to top-level module properties; named exports win over frontmatter on collisions.
- **User remark plugins run *after* the frontmatter pair.** `pkg.xtatic.remarkPlugins` is read by `cli.js`, threaded through `build()` → `createRegistry()` → `compileSource()`, and appended after `[remarkFrontmatter, remarkMdxFrontmatter]` so user plugins never see the YAML block (it's already an MDX export node by then). Each entry is either a bare string (`"remark-foo"`) or a tuple (`["remark-foo", opts]`); `cli.js` resolves names via `createRequire(topDir/package.json)` so plugins are looked up in the *user's* `node_modules`, not xtatic's. The `build()` API itself takes already-loaded plugin functions/tuples — no resolution there.
- **`remark-smartypants` is on by default at the CLI layer.** `cli.js` prepends it to `remarkPlugins` (so it runs first, after the frontmatter pair inside `compile.js`). `pkg.xtatic.smartypants` controls it: `true`/absent = on with default options, `false` = off, an object = on with that as the plugin's options. The default is wired in `cli.js` only — `build()` itself gets no smartypants unless the caller passes it in. Tests that drive `build()` directly (most of the suite) are therefore unaffected.
- **The layout chain is bounded** at depth 100 in `render.js` to catch self-referential cycles.
- **A module's own properties leak into JSX expressions as bare identifiers.** `recma-self.js` scope-analyzes `_createMdxContent`, finds otherwise-unbound identifiers, and prepends `const { … } = props.__xtatic_self ?? {};`. `registry.js` wraps `mm.default` so every render call passes `__xtatic_self: mm`, and the closure captures the live `mm` (so `childPages`/`layout` added later by `tree.js` are visible). Built-in globals (`Math`, `Array`, …) are filtered out so they don't get accidentally shadowed; novel free identifiers that don't exist on `mm` simply destructure to `undefined`.
- **Builtins are imported explicitly via the `xtatic:` scheme.** `src/builtins.js` exports `html(s) → {html: String(s)}` and `makeReadfile({fs, topDir, importerAbsPath, importerDisplay}) → readfile(spec)`. User code writes `import {html, readfile, asset} from 'xtatic:builtins'`; the resolver in `registry.js` (`makeResolver`) returns a fresh `{html, readfile, asset}` per importer, with `readfile` closed over the importer's path so relative-spec resolution works. `asset` is the same per-importer function that recma-assets wires up under the hood for whitelisted JSX attributes — useful when you need to call it from places the recma plugin can't catch (non-whitelisted attrs, JS expressions, etc.). `recma-imports.js`'s `SPEC_RE` accepts `^xtatic:[a-z][a-z0-9-]*$` so the rewrite to `__xtatic_resolve(spec)` fires — same path used for ordinary user imports. There is no ambient binding in either `.md`/`.mdx` or `.jsx`: omit the import and the name is free for the user to define. `readfile` is sync (JSX expressions render synchronously, so no `fs.promises` here); paths starting with `/` resolve against `topDir`, everything else (including bare names) resolves against the module's own directory — matching POSIX intuition rather than `import`'s npm-flavored "no bare specs" rule. The known set of `xtatic:*` modules and their exports lives in `src/builtins-registry.js` — both `makeResolver` (for the runtime "Unknown builtin module" error) and the lint rule `xtatic/builtin-imports` (for compile-time validation) consume it, so they can't drift.
- **Lint runs at the CLI layer, not inside `build()`.** `src/cli.js` calls `runLint({topDir, outputDir})` from `src/lint.js` *before* `build()`; a lint failure exits 1 with the formatted ESLint output and no build artifacts are written. `build()` itself stays a pure data transform with no `eslint` dependency, so memfs-injected tests are untouched (most of the suite never goes through lint). The lint phase is real-fs only — it walks the topDir tree (skipping `outputDir` and `node_modules`) and runs ESLint programmatically over `**/*.{md,mdx,jsx,js}`. Only the `cli.test.js` and `lint.test.js` real-fs scratch tests exercise the integrated lint path; all other tests bypass lint by calling `build()` directly. There is no opt-out today (no `--no-lint` flag, no `pkg.xtatic.lint: false`); add one when someone needs faster iteration.
- **The opinionated lint config** lives in `src/lint.js` `makeConfig()` and ships frozen — there is no user override yet (planned). Rule set is import-correctness only: `import/no-unresolved` (with `^xtatic:` ignored — the custom rule covers those), `import/named`, `import/no-duplicates`, `xtatic/builtin-imports` for `.md`/`.mdx`/`.jsx`/`.js`, plus `import/default` and `no-undef` for `.js`/`.jsx` only. `import/default` is **off** for `.md`/`.mdx` because xtatic's default-import semantics there bind the whole module object rather than `mm.default` (the documented divergence) — the rule would still pass since `.mdx` files always have a `default` export, but it's cheaper to disable than to reason about. `eslint-plugin-mdx` provides the `.md`/`.mdx` parser via its `flat` config preset; `eslint-plugin-import` and `eslint` are hard `dependencies`, not optional. Custom rules live under `src/eslint-rules/`.
- **`.md` is parsed as MDX, not plain Markdown, by lint.** `eslint-mdx` defaults to treating only `.mdx` as MDX and `.md` as plain markdown (where `import` lines are just text and never reach the import-correctness rules). Xtatic compiles both extensions through @mdx-js/mdx, so the lint config passes `parserOptions.extensions: ['.md']` to flip `.md` into the MDX parser path. Without this, broken imports inside `layouts/default.md` (or any `.md` file) sail through lint and only blow up at render with "Unsupported JSX type: undefined". Also disables `no-unused-expressions` for `.md`/`.mdx` because the `eslint-plugin-mdx` flat preset turns it on and it false-positives on bare JSX expressions like `<Foo />` (which IS the rendered output in MDX).
- **Imports are rewritten by a recma plugin, not real `import()`.** `compile.js` calls `@mdx-js/mdx`'s `compile` directly (not `evaluate`), runs the result via `new AsyncFunction(body)`, and passes a `__xtatic_resolve` closure through `arguments[0]`. `recma-imports.js` rewrites every `await import('<spec>')` MDX produced into `await arguments[0].__xtatic_resolve('<spec>')`. The dummy `baseUrl: 'file:///xtatic/'` is required only to suppress MDX's runtime baseUrl check; it's never actually used because we removed every real `import()`.
- **`.md`/`.mdx` default-import semantics differ from ESM.** `import X from './foo.mdx'` binds X to the *whole module object*, not `mm.default`. The recma plugin enforces this by splitting the destructure: `const ns = await __xtatic_resolve(spec); const X = ns; const {a, b} = ns;` for any `default` key in the pattern. `.js` keeps standard ESM semantics (default = `.default`).
- **Cycles work via a stable placeholder identity.** `registry.js`'s `loadMdx` sets `mdxModules.set(absPath, {mm: {}, status: 'compiling'})` *before* awaiting source/compile, so a circular re-entry returns the same `mm` object reference. After compile, `Object.assign(mm, compiled)` mutates the placeholder in place — anyone holding the reference sees the final shape by render time.
- **`.js` files do not go through MDX.** They're loaded via real `import(pathToFileURL(absPath).href)`, so relative `.js`→`.js` imports and bare specifiers (npm, `node:`) resolve via Node's normal resolver. `.js`→`.md`/`.mdx` is still unsupported (Node doesn't know how to load `.mdx`).
- **`.jsx` files have their own compile pipeline in `src/compile-jsx.js`.** They're parsed with `acorn` extended by `acorn-jsx`, JSX is lowered by `estree-util-build-jsx` (automatic runtime, `importSource: '__xtatic_internal_jsx_runtime'`), `transformModule` strips the auto-import (re-emits it as a destructure from `arguments[0]`), expands user `ImportDeclaration`s into MDX-style `await import(...)` patterns so `recmaImports` can rewrite them, and rewrites `export` declarations into a single `return { … }` statement. Then `astring` serializes and the body runs in `new AsyncFunction(body)`. Same dependency footprint as `.mdx` — no new direct deps; `acorn`, `acorn-jsx`, `estree-util-build-jsx`, and `astring` are all transitive via `@mdx-js/mdx`.
- **`.jsx` differs from `.mdx` deliberately.** No `recma-self` (so module properties don't leak as bare identifiers — pure JS scoping), no frontmatter, no markdown body. Default-import semantics are ESM (`import X from './x.jsx'` binds `X` to `mm.default`), the same as `.js` and unlike `.md`/`.mdx`. `.jsx` files are also **not auto-promoted to pages** — `walkMdx` ignores them; they only enter the build via `import`. Builtins (`html`, `readfile`, `asset`) work identically to `.mdx`: import from `xtatic:builtins`, no ambient binding. recma-assets runs in `compile-jsx.js` too (after `recmaImports`, before code generation), so plain `<img>`/`<link>`/etc. inside `.jsx` get the same auto-asset processing.

## JSX shim cheat sheet

`src/jsx-runtime.js` returns `{html: string}` directly — no VDOM. Exports `jsx`, `jsxs` (alias), `Fragment`. Tag types: string (HTML element), function (component), or module object (calls `mm.default`). Children: HTML objects pass through unescaped; modules render via `mm.default({})`; primitives are HTML-escaped; null/undefined/booleans render empty; arrays flatten. Attribute renames: `className` → `class`, `htmlFor` → `for`. Booleans use HTML conventions (bare on `true`, omitted on `false`/`null`/`undefined`).

## Workflow

- `npm test` runs the full Node test suite. Three flavors:
  - **memfs tests** (most of them) inject a memfs `fs`; nothing touches disk.
  - **real-fs tests** (`test/cli.test.js`, `test/imports-js.test.js`, `test/smoke.test.js`, `test/remark-plugins.test.js`) scratch under `./test-tmp/<file>/...`. Each file's top-level `before` wipes only its own subtree (test files run in parallel, so a file-wide wipe of `test-tmp/` will race other files' fixtures). `test-tmp/` is gitignored. Slugs must be unique per test in the file — Node caches `import()` by URL, so reusing a slug serves stale `.js` content.
  - The smoke test passes no fs injection, exercising the default `node:fs` code path end-to-end.
- **After making a change and seeing the suite green, commit immediately — don't wait to be asked.** Don't batch unrelated changes; checkpoint often.
- ESM only — `package.json` has `"type": "module"`, all imports use explicit `.js` extensions.

## Known scope cuts (deliberate)

- `style` prop accepts strings only; object form (`style={{color: 'red'}}`) stringifies as `[object Object]`.
- Components are synchronous; async MDX components aren't supported.
- POSIX path separators only; not tested on Windows.
